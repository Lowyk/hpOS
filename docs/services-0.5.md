# Службы и рабочий стол 0.5

Версия добавляет службу ввода (процесс 3) и службу рабочего стола (процесс 4).
Обе — отдельные Rust `no_std` ELF-программы, собранные Clang/LLVM/Rust-цепочкой
без внешних пакетов. Python упаковывает PT_LOAD, включая `.bss`, и встраивает
образы в read-only секцию ядра. При загрузке каждому процессу выделяются свои
физические страницы с правами секций. Ping/Pong остаются процессами 1/2;
ядро обслуживания и idle — потоки 0/5.

## Разделение полномочий

| Компонент | Доступ и работа |
|---|---|
| IRQ1 в ядре | читает PS/2, отбрасывает aux-байты, ставит scan codes в очередь, посылает EOI |
| Служба ввода | получает сырые байты через ограниченный вызов, разбирает set 1, отправляет события |
| Служба рабочего стола | получает события, рисует в своём framebuffer mapping, читает диагностику |
| Поток ядра | выполняет запрошенную самопроверку памяти, сохраняет аварийную диагностику |
| Ping/Pong | продолжают проверять IPC, последовательность и приватную память |

В ядре больше нет назначения клавиш T/M или штатной перерисовки рабочего стола.
Полного переноса аппаратного драйвера PS/2 пока нет: минимальный IRQ-stub
с чтением портов остаётся в ядре, прямые порты пользовательским процессам
не разрешены. Права на ресурсы статические, выдаются при загрузке.

Сырые байты доступны только процессу 3. Процесс 4 при запуске проверяет, что
его попытка прочитать их получает Denied. Запрос проверки памяти доступен
только процессу 4; процесс 3 проверяет отказ. Фреймбуфер отображён только
в адресном пространстве процесса 4; при построении других пространств ядро
проверяет отсутствие отображения. Эти проверки дополняют прежние probes:
каждый из четырёх процессов проверяет отказ чтения страницы ядра и отправки
через Receive-handle. `ISOLATION OK` требует прохождения этих прежних probes
для всех четырёх процессов; дополнительные проверки ресурсов выполняются отдельно.

Служба ввода имеет handle 0 Send в endpoint 2. Рабочий стол имеет handle 1
Receive из endpoint 2. Endpoint 3 зарезервирован для обратного направления,
handle 1 ввода / handle 0 рабочего стола; обычный обмен туда ещё не используется.
Очереди IPC увеличены до 32 сообщений. MESSAGES включает и Ping/Pong, и события
клавиатуры. Служба рабочего стола проверяет sender 3 перед обработкой события.

Очередь IRQ содержит максимум 63 сырых байта. Она не перезаписывает старые
данные при переполнении; счётчик потерь показывается как `KEY QUEUE OVERFLOW`.
После потери scan codes состояние клавиш может потребовать повторного отпускания
или нового нажатия; автоматической ресинхронизации PS/2 пока нет.
Декодер подавляет typematic-повторы и различает make/break, E0 и последовательность
Pause E1. Кириллица и ввод произвольного текста будут отдельным этапом.

## Память и ABI

В 0.5 пользовательская область начинается с `0xffffffff80000000` (PML4 slot 511).
Это позволяет использовать code model kernel, совместимый с поставляемой Rust
`core` и LTO. CPU разрешает пользовательский доступ к canonical high addresses
при U/S на всех уровнях. Общие страницы ядра в slot 0 остаются supervisor-only.
Назначение областей относительно пользовательского начала сохраняется:

- от 0: загруженные страницы text, rodata, data/bss ELF-службы;
- `0x100000`: приватная страница маркера и Startup, структура Startup по смещению 16;
- `0x201000`–`0x204fff`: пользовательский стек, guard-страницы снаружи;
- `0x1000000`: выделенное отображение VBE только для рабочего стола, uncached.

Startup содержит виртуальный адрес фреймбуфера, ширину, высоту и stride;
физический адрес, E820 и прочие загрузочные данные службе не передаются.
При отсутствии VBE рабочий стол работает без рисования, ядро сообщает о
текстовом fallback. Ядро проверяет различие CR3 и приватных страниц всех процессов.
IST double fault перенесён, чтобы не пересекаться со стеком нового idle.

Прежние вызовы 0–4 сохранены. Дополнительные вызовы используют тот же `INT 0x80`:

| RAX | Назначение | Доступ / результат |
|---|---|---|
| 5 | GetStatus | только процесс 4; RDI: поле 0–14, RDX: значение |
| 6 | ReadScanCode | только процесс 3; RDX: байт, статус 1 если очередь пуста |
| 8 | RequestMemoryCheck | только процесс 4; асинхронный запрос ядру |

Поля GetStatus: ticks, switches, ping, pong, messages, isolation, checks, free MiB,
NX, error, key events, frames, dropped bytes, fault (vector + 1, 0 если отсутствует),
heartbeat ввода. Это диагностический ABI; отдельные чтения не дают атомарного
снимка всех счётчиков. Быстрые повторные запросы M могут объединяться в одну
проверку. Ошибка рабочего стола останавливает этот процесс и выводит сохранённый
аварийный экран ядра; автоматического перезапуска служб ещё нет.

## Интерфейс

Рабочий стол имеет светлую/тёмную тему, панель задач, меню и два внутренних окна:
SYSTEM с диагностикой и HELP с клавишами. Это первая оболочка с управлением
клавиатурой. Мыши, перетаскивания, одновременных окон приложений, файлов,
редактора и терминала в этой версии ещё нет. ASCII-шрифт остаётся временным.

| Клавиша | Действие |
|---|---|
| T | сменить тему |
| M | запросить проверку памяти |
| F1 / F2 | открыть SYSTEM / HELP |
| Tab | переключить окно |
| Space или Windows | открыть/закрыть меню |
| Стрелки вверх/вниз, Enter | выбрать и открыть пункт меню |
| Esc | закрыть меню, затем окно |

Полная перерисовка выполняется при смене состояния; обычные счётчики обновляются
раз в 20 тиков, примерно 5 Гц. Это частота обновления диагностики, не обещание
FPS анимаций. Открытое меню не затирается частичной перерисовкой окна.
FRAMES считает завершённые проходы обновления, даже когда окно закрыто.

## Проверки

Host-тесты проверяют FIFO сырых байтов и переполнение, Startup ABI, разбор
scan codes, переходы меню и окон, clipping с сохранением padding, ограничение
framebuffer mapping одним адресным пространством и ELF-границы служб.
Визуальные превью получены тем же Rust-кодом рисования в 800×600 и 1024×768
для двух тем, окон SYSTEM/HELP и меню. Данные в превью примерные; это не
снимки запущенной ОС. IRQ-entry и пользовательские entry points проверяются
статическим дизассемблированием. Эти проверки не подтверждают запуск 0.5 на CPU.

Для готового образа прошли 34 Rust-теста, 7 Python-тестов, release-сборка
и проверка форматирования. Хеши образов 0.1–0.4 в сохранённых каталогах
повторно проверены и совпадают с их manifest.

Запуск образа 0.5 подтверждён последующим сообщением пользователя;
копия сохранена в `build/verified-0.5/hpos.img`. Отдельные действия ниже
не зафиксированы в сообщении.
`build/verified-0.4/hpos.img` сохранён для отката.

1. Загрузить 0.5 прежним способом; стартовая диагностика должна смениться рабочим столом.
2. В SYSTEM дождаться IPC OK, ISOLATION OK, MEMORY OK и INPUT OK; PING/PONG,
   MESSAGES, SWITCHES, FRAMES и число секунд должны расти.
3. Нажать T с отпусканием несколько раз: темы меняются, счётчики работают.
4. Нажимать M с паузами: CHECKS растёт, FREE MIB остаётся стабильным.
5. Проверить F2, Tab, Esc, F1: окна меняются, закрываются и снова открываются.
6. Нажать Space, выбрать HELP стрелкой и Enter; затем закрыть меню клавишей Esc.
7. Вернуться F1, проверить рост KEY EVENTS и отсутствие SERVICE ERROR,
   KEY QUEUE OVERFLOW, PROCESS FAULT. Оставить на несколько минут и сохранить фото.

NX пока не расследуется; NX NOT AVAILABLE не считается ошибкой этого этапа.
