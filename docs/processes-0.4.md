# Пользовательские процессы и IPC 0.4

Версия добавляет два статических процесса Ping/Pong в ring 3. Они обмениваются
нумерованными 64-битными сообщениями и проверяют отправителя и порядок.
Интерфейс диагностики и idle остаются потоками ядра. Планирование выполняется
на одном CPU; второй процессор пока не запускается.

## Адресные пространства и переходы

У каждого процесса свой PML4 и CR3. Слот 0 PML4 импортирует общие таблицы ядра
без права пользовательского доступа; слот 1 содержит собственные страницы
процесса, начинающиеся с `0x8000000000` (512 ГиБ).

| Смещение от начала пользовательской области | Назначение |
|---|---|
| `0` | одна страница кода, read-only, executable |
| `0x100000` | собственная страница данных, writable |
| `0x200000` | отсутствующая нижняя guard-страница |
| `0x201000`–`0x204fff` | четыре страницы пользовательского стека |
| `0x205000` | отсутствующая верхняя guard-страница |

Биты U/S выставляются на всех уровнях пользовательского отображения. Mapper
отказывается превращать существующего supervisor-предка в user-предка.
Физические страницы двух процессов различаются. Ядро видит физическую память
через своё supervisor identity mapping, пользовательские процессы — только
собственные отображения. Без NX страницы данных и стека остаются исполняемыми;
защита от чтения памяти ядра и других процессов от NX не зависит.

GDT содержит пользовательские CS `0x2b` и SS `0x33`. TSS задаёт RSP0 для
перехода в ядро и отдельный IST1 для double fault. Для каждого процесса выделен
отдельный стек ядра с guard-страницами. Системные вызовы используют interrupt
gate `INT 0x80` с DPL 3; программный yield ядра `INT 0x30` остаётся DPL 0.
IOPL равен нулю, I/O bitmap находится за пределом TSS: прямой доступ процесса
к портам запрещён. Перед возвратом проверяются CS, SS, RIP и RSP; CR3 меняется
при выборе другого адресного пространства. Сохраняются общие регистры
и состояние x87/SSE через FXSAVE64/FXRSTOR64.

Пользовательская программа — небольшой копируемый ассемблерный блок с локальными
переходами, без внешних ссылок. Загрузчик пользовательских ELF ещё не реализован.

## Временный ABI

Номер вызова передаётся в RAX, аргументы — в RDI и RSI. RAX возвращает статус:
0 — успех, 1 — пустая/полная очередь, 2 — неверный handle или объект,
3 — отказ по правам, 4 — неверный вызов или диагностическая ошибка.

| RAX | Операция | Аргументы / результат |
|---|---|---|
| 0 | Sleep | RDI: число тиков, максимум 10000; 0 уступает очередь |
| 1 | Send | RDI: handle, RSI: 64-битное слово |
| 2 | Receive | RDI: handle; при успехе RDX: слово, RCX: отправитель 1 или 2 |
| 3 | Report | RDI: следующий номер успешно завершённого обмена |
| 4 | ReportFailure | устанавливает постоянный индикатор ошибки теста |

Report и ReportFailure нужны только диагностике этой версии. Это предварительный
ABI, без пользовательских указателей, передачи буферов и общего списка процессов.
Остальные регистры сохраняются; Receive обновляет RDX и RCX только при успехе.

У каждого процесса handle 0 даёт Send в очередь соседа, handle 1 — Receive
из собственной очереди. Ядро выдаёт права при запуске; процесс не может сам
выбрать endpoint, поменять право или подделать отправителя. В каждой FIFO-очереди
восемь сообщений. Полная очередь возвращает отказ без потери старых сообщений;
пустая — отказ без блокировки. Демонстрационные процессы спят один тик и повторяют
операцию, затем делают паузу пять тиков после успешного обмена.

## Проверка изоляции и ошибок

В начале каждый процесс намеренно читает адрес `0x100000` — страницу ядра.
Ожидается protection page fault из ring 3. Только для известной инструкции,
адреса и корректного пользовательского стека обработчик фиксирует успех
и переводит RIP на продолжение теста. Затем процесс пробует Send через
Receive-handle и проверяет статус Denied. `ISOLATION OK` требует успеха обеих
проверок для обоих процессов. Если чтение ядра неожиданно разрешено, процесс
сообщает об ошибке.

Маркер собственной страницы данных и пользовательского стека проверяется во
время обмена; ядро также проверяет маркер и последовательность Report.
`IPC OK` требует ненулевых счётчиков обоих процессов, переключений контекста
и отсутствия зарегистрированных ошибок. Это диагностические probes, не полный
аудит безопасности микроядра.

Неожиданные пользовательские #PF, #GP, #UD и #DE останавливают текущий процесс
и оставляют остальные задачи работать. На экране появляется ошибка IPC и номер
исключения. Остальные исключения пока завершают работу ядра. При этих четырёх
исключениях в kernel mode выводится аварийная диагностика VECTOR, ERROR, RIP
и ADDRESS, затем CPU останавливается. ADDRESS взят из CR2 и имеет смысл для #PF.

Страницы и таблицы процессов выделяются только при загрузке и остаются занятыми
до перезагрузки, включая остановленные процессы. При неудаче создания процессного
пространства запуск останавливается; частично выделенные ресурсы ещё не возвращаются.
Динамическое создание/уничтожение процессов, SMP, блокирующий IPC, передача прав,
разделяемые буферы и пользовательские драйверы — следующие этапы.

## Аппаратная проверка

Образ: `build/hpos-0.4.img`, 32 МиБ. Аппаратный запуск подтверждён сообщением
и фото пользователя: IPC OK, ISOLATION OK, PING/PONG по 1509, MESSAGES 3018.
Проверенная копия сохранена в `build/verified-0.4/hpos.img`, её manifest имеет
`boot_tested: true`. Полный результат — в [hardware-tests.md](hardware-tests.md).
Рабочая версия 0.3 сохранена в `build/verified-0.3/hpos.img` и не перезаписывается
сборкой. Каждый новый образ требуется проверить отдельно; новая сборка
всегда создаёт manifest с `boot_tested: false`.

1. Загрузить 0.4 тем же способом, которым загрузилась 0.3.
2. Подождать несколько секунд: ожидаются `MEMORY OK`, `IPC OK`, `ISOLATION OK`.
3. Убедиться, что PING, PONG, MESSAGES, TICKS и SWITCHES увеличиваются.
   PING и PONG могут временно отличаться на один завершённый обмен.
4. Нажать M несколько раз: CHECKS растёт, свободная память остаётся стабильной.
5. Переключить T несколько раз: темы меняются, обмен продолжается.
6. Оставить систему работать несколько минут; сохранить фото состояния.
   При ошибке сохранить фото с индикатором или аварийными полями.

На host прошли 27 Rust-тестов и 6 Python-тестов. Проверены политика остановки,
права IPC, FIFO, отдельные адресные пространства, supervisor-доступ и ELF-границы
пользовательского блока. Сборка release и форматирование прошли; машинный код
пользовательского блока и возврата из fault handler проверен статическим
дизассемблированием. Эти проверки не подтверждают фактический вход в ring 3,
работу TSS, IRQ и IPC на физическом CPU: это проверяет новый запуск на ноутбуке.
